## Findings

### SA-001: NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY publishes a secret to the browser

- **Severity:** Critical
- **Rule:** `secret-in-client`
- **Location:** `.env.local:3`

**Why it matters.** Next.js inlines every NEXT_PUBLIC_ variable into the client bundle at build time (env file). A name containing a secret marker means the value is readable by every visitor.

**Evidence**

```
NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY=…
```

**Recommended fix.** Rename the variable without the NEXT_PUBLIC_ prefix, read it only in route handlers or server components, and rotate the key because it has already been exposed.

### SA-008: Write on notes filtered only by id from the request

- **Severity:** High
- **Rule:** `api-idor`
- **Location:** `app/actions.ts:6`

**Why it matters.** The record is chosen by id, which the caller controls, and the query has no filter on the signed-in user. Changing the id in the request reaches other users' records. If row level security already restricts this table to the owner and the query runs with the user's own client, this is defense in depth; with a service-role or admin client it is the only check.

**Evidence**

```
await supabase.from("notes").delete().eq("id", noteId);
```

**Recommended fix.** Add an ownership condition taken from the session (for example .eq("user_id", user.id) or where: { id, userId: session.user.id }) and treat zero matched rows as 404.

### SA-016: Request body is parsed before the signature is verified

- **Severity:** High
- **Rule:** `stripe-webhook-parse-before-verify`
- **Location:** `app/api/stripe/webhook/route.ts:8`

**Why it matters.** The signature covers the exact bytes Stripe sent. Parsing the body first and re-serialising it changes those bytes, so verification fails in production. The usual workaround, trusting the parsed body and dropping verification, removes the protection altogether.

**Evidence**

```
const body = await request.json();
```

**Recommended fix.** Use "const rawBody = await request.text()" and pass rawBody to constructEvent; parse JSON only from the verified event.

### SA-028: Unhandled event types make the handler fail (returns 500)

- **Severity:** Low
- **Rule:** `stripe-webhook-unknown-event-error`
- **Location:** `app/api/stripe/webhook/route.ts:34`

**Why it matters.** Stripe sends every event type the endpoint is subscribed to. A non-2xx answer for an event you simply do not handle is retried for days and, after repeated failures, the endpoint is disabled, which then also drops the events you do care about.

**Evidence**

```

```

**Recommended fix.** Return 200 for unhandled types (log them) and reserve error statuses for events you tried to process and failed. Subscribe the endpoint only to the events you handle.

**Recommended fix.** Return the headers from an async headers() function in next.config for source "/(.*)": X-Content-Type-Options nosniff, X-Frame-Options DENY, Referrer-Policy strict-origin-when-cross-origin, Strict-Transport-Security, and a Content-Security-Policy suited to the app.

## What was not checked

For this project in particular:

- No readable .git/index at the project root: whether .env files are tracked was judged from .gitignore rules only.

In general:

- Runtime behaviour. Nothing was executed, no request was sent and no database was queried. Row level security is judged from the SQL in the migrations, not from the policies that are live in a database.
- Anything configured outside the repository: Supabase dashboard settings (auth providers, redirect URL allow-list, email confirmation, storage bucket policies), Stripe dashboard settings and webhook endpoints, hosting environment variables, DNS, CDN and WAF rules.
- Database objects other than tables and policies: views (security_invoker), SECURITY DEFINER functions, grants, triggers, extensions and realtime publications.
- Authorization logic beyond the patterns the rules recognise. A route that calls an auth helper is treated as authenticated; whether the check is correct, complete or applied to every branch is not evaluated. Business-rule authorization (roles, plans, seat limits) is not evaluated.
- Data flow across files. Taint is tracked inside one function; values that pass through an imported helper are treated as no longer client-controlled, and imported data-access helpers are not followed.
- Dependency vulnerabilities. There is no advisory database in this tool; run npm audit (or your package manager's equivalent) and review lockfile changes.
- Secrets in git history, in build artifacts, in files outside the scanned extensions, and in third-party services.
- Denial of service, performance, accessibility, privacy and legal compliance, and any vulnerability class not named in the rule list below.
- Findings are candidates with evidence, not proof of exploitability. False positives are possible and a clean report is not evidence that the application is secure.
