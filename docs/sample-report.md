## Findings

### SA-001: POST handler writes data without an auth check

- **Severity:** Critical
- **Rule:** `api-route-no-auth`
- **Location:** `app/api/generate/route.ts:4`

**Why it matters.** No call to a recognised auth helper (getUser, getSession, auth, requireUser, ...) was found in this handler. Route handlers are reachable by anyone who knows the URL, and middleware alone is not a reliable gate.

**Evidence**

```
L4: export async function POST(request: Request) {
L6: const { data } = await admin
```

**Recommended fix.** Resolve the user at the top of the handler and return 401 when there is none, then scope every query to that user. If the route is public on purpose, list it in publicRoutes in saas-audit.config.json or add a saas-audit-ignore-file comment with the reason. Custom helpers can be added with authHelpers.

### SA-002: Table public.credit_ledger has no row level security

- **Severity:** Critical
- **Rule:** `supabase-rls-missing`
- **Location:** `supabase/migrations/0001_init.sql:17`

**Why it matters.** Tables in the public schema are exposed through the REST API to anyone with the anon key. Without ENABLE ROW LEVEL SECURITY every row can be read (credit_ledger has user_id, so these are per-user rows) and, with the default grants, written.

**Evidence**

```
create table public.credit_ledger (
```

**Recommended fix.** Add "alter table public.credit_ledger enable row level security;" in a migration, then add policies for each operation the app needs.

### SA-003: Stripe billingPortal.sessions.create uses an id from the request

- **Severity:** High
- **Rule:** `stripe-customer-unchecked`
- **Location:** `app/api/billing/portal/route.ts:13`

**Why it matters.** Nothing ties the id to the signed-in user, so a caller can pass another customer's id and open their billing portal, read or cancel their subscription, or refund their payment.

**Evidence**

```
customer: customerId,
```

**Recommended fix.** Resolve the customer from the authenticated user (a stripe_customer_id column looked up by session user id) and ignore any id in the request. If an id must be accepted, compare it to that stored value first.

### SA-004: Row owner user_id is set from the request

- **Severity:** High
- **Rule:** `api-idor`
- **Location:** `app/api/generate/route.ts:8`

**Why it matters.** The insert writes user_id with a value supplied by the caller, so anyone can create or reassign rows for other users or tenants.

**Evidence**

```
.insert({ user_id: userId, prompt })
```

**Recommended fix.** Set user_id from the verified session (user.id) on the server and never read it from the body.

### SA-005: Client component reads server secret STRIPE_SECRET_KEY

- **Severity:** High
- **Rule:** `secret-in-client`
- **Location:** `components/Dashboard.tsx:4`

**Why it matters.** This file starts with "use client", so it is bundled for the browser. Non-public environment variables are not available there; code that needs STRIPE_SECRET_KEY in the browser is either broken or one rename away from publishing it as NEXT_PUBLIC_.

**Evidence**

```
const key = process.env.STRIPE_SECRET_KEY;
```

**Recommended fix.** Move the call that needs the secret into a route handler, server action or server component and call that from the client component.

### SA-006: dangerouslySetInnerHTML receives non-constant input

- **Severity:** High
- **Rule:** `unsafe-html`
- **Location:** `components/Dashboard.tsx:5`

**Why it matters.** Anything that reaches this sink is parsed as HTML in the visitor's browser. If any part of it comes from a user, a database row or a third-party API, that is stored or reflected cross-site scripting, and an XSS bug can read the session and call every API as the user.

**Evidence**

```
return <div data-configured={Boolean(key)} dangerouslySetInnerHTML={{ __html: html }} />;
```

**Recommended fix.** Render the value as text (JSX escapes it). If HTML is required, sanitize it on the server with an allow-list sanitizer first and pass the result, or render Markdown with raw HTML disabled.

### SA-007: No policy on generations ties user_id to the caller

- **Location:** `supabase/migrations/0001_init.sql:9`

**Why it matters.** generations has user_id to identify who owns a row, but none of its 1 policy compares it with auth.uid() or passes it to a membership function. Any user the policies admit can reach every other user's or tenant's rows.

**Evidence**

```

```

### SA-008: Policy "members readable" lets every role including anon read every row of members

- **Severity:** High
- **Rule:** `supabase-policy-permissive`
- **Location:** `supabase/migrations/0002_policies.sql:6`

**Why it matters.** USING (true) is always true. members has an owner column, so this exposes every user's rows.

**Evidence**

```
create policy "members readable" on public.members
```

**Recommended fix.** Scope the policy to the caller (auth.uid() = owner column). If the table is public on purpose, keep the policy and add a saas-audit-ignore-next-line comment with the reason.

**Evidence**

### SA-011: Read on generations filtered only by id from the request

- **Severity:** Medium
- **Rule:** `api-idor`
- **Location:** `app/api/generations/[id]/route.ts:10`

**Why it matters.** The record is chosen by id, which the caller controls, and the query has no filter on the signed-in user. Changing the id in the request reaches other users' records. If row level security already restricts this table to the owner and the query runs with the user's own client, this is defense in depth; with a service-role or admin client it is the only check.

**Evidence**

```
const { data } = await admin.from("generations").select("*").eq("id", id).single();
```

**Recommended fix.** Add an ownership condition taken from the session (for example .eq("user_id", user.id) or where: { id, userId: session.user.id }) and treat zero matched rows as 404.

### SA-012: Webhook does not deduplicate events

- **Severity:** Medium
- **Rule:** `stripe-webhook-no-idempotency`
- **Location:** `app/api/stripe/webhook/route.ts:10`

**Why it matters.** Stripe delivers events at least once and retries on any non-2xx answer, so the same event can arrive twice. Without a stored event.id, fulfilment code (credits, emails, plan changes) runs twice.

**Evidence**

```
const event = stripe.webhooks.constructEvent(payload, signature, process.env.STRIPE_WEBHOOK_SECRET!);
```

**Recommended fix.** Insert event.id into a table with a unique constraint before doing the work (on conflict do nothing) and return 200 early when the row already existed. Do the insert and the work in one transaction.

### SA-013: next build ignores TypeScript errors

- **Severity:** Medium
- **Rule:** `build-checks-disabled`
- **Location:** `next.config.mjs:3`

**Why it matters.** Type errors ship to production unnoticed. Generated code that does not compile often contains exactly the wrong-argument and missing-await mistakes that cause security and billing bugs, and this switch hides them.

**Evidence**

```
typescript: { ignoreBuildErrors: true },
```

**Recommended fix.** Remove the flag and fix the type errors (npx tsc --noEmit lists them). Run the check in CI so it cannot regress.

**Why it matters.** With RLS on and no policy, anon and authenticated clients are denied every operation. Either the table is only used through the service role, or the app is broken and the quick fix will be to switch RLS off or add a policy with USING (true).

**Evidence**

```
create table public.waitlist (

### SA-015: Unhandled event types make the handler fail (returns 500)

- **Severity:** Low
- **Rule:** `stripe-webhook-unknown-event-error`
- **Location:** `app/api/stripe/webhook/route.ts:24`

**Why it matters.** Stripe sends every event type the endpoint is subscribed to. A non-2xx answer for an event you simply do not handle is retried for days and, after repeated failures, the endpoint is disabled, which then also drops the events you do care about.

**Evidence**

```
return NextResponse.json({ error: `Unhandled event ${event.type}` }, { status: 500 });
```

**Recommended fix.** Return 200 for unhandled types (log them) and reserve error statuses for events you tried to process and failed. Subscribe the endpoint only to the events you handle.

### SA-017: next is declared as "latest"

- **Severity:** Low
- **Rule:** `deps-unpinned`
- **Location:** `package.json:11`

**Why it matters.** Every install can resolve to a different major version, including one published minutes ago. Builds stop being reproducible and a compromised release is picked up automatically.

**Evidence**

```

**Recommended fix.** Pin next to the version in use (npm install 'next\@\<version>' --save-exact) and commit the lockfile.

**Why it matters.** Login, password reset, token and webhook endpoints are brute-force and cost-amplification targets. No rate limiter, throttle or middleware limiter was found in this file or in the middleware. Informational: the platform in front of the app may already provide one.

**Evidence**

### SA-019: No security headers are configured

- **Severity:** Info
- **Rule:** `security-headers`
- **Location:** `next.config.mjs:1`

**Why it matters.** No Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Strict-Transport-Security or Referrer-Policy header is set in next.config or anywhere in the source. The hosting platform may add some; Next.js adds none by default.

**Evidence**

```
/** @type {import('next').NextConfig} */
```

**Recommended fix.** Return the headers from an async headers() function in next.config for source "/(.\*)": X-Content-Type-Options nosniff, X-Frame-Options DENY, Referrer-Policy strict-origin-when-cross-origin, Strict-Transport-Security, and a Content-Security-Policy suited to the app.

## What was not checked

For this project in particular:

- No readable .git/index at the project root: whether .env files are tracked was judged from .gitignore rules only.

In general:

- Runtime behaviour. Nothing was executed, no request was sent and no database was queried. Row level security is judged from the SQL in the migrations, not from the policies that are live in a database.
- Anything configured outside the repository: Supabase dashboard settings (auth providers, redirect URL allow-list, email confirmation, storage bucket policies), Stripe dashboard settings and webhook endpoints, hosting environment variables, DNS, CDN and WAF rules.
- Database objects other than tables and policies: views (security_invoker), SECURITY DEFINER functions, grants, triggers, extensions and realtime publications. Policies and RLS statements inside DO blocks, functions or EXECUTE are not interpreted; a warning is printed when they are found.
- Authorization logic beyond the patterns the rules recognise. A route that calls an auth helper is treated as authenticated; whether the check is correct, complete or applied to every branch is not evaluated. Business-rule authorization (roles, plans, seat limits) is not evaluated.
- Data flow across files. Taint is tracked inside one function; values that pass through an imported helper are treated as no longer client-controlled, and imported data-access helpers are not followed.
- Dependency vulnerabilities. There is no advisory database in this tool; run npm audit (or your package manager's equivalent) and review lockfile changes.
- Secrets in git history, in build artifacts, in files outside the scanned extensions, and in third-party services. A secret split across string concatenations or built at run time is not recognised.
- Denial of service, performance, accessibility, privacy and legal compliance, and any vulnerability class not named in the rule list below.
- Findings are candidates with evidence, not proof of exploitability. False positives are possible and a clean report is not evidence that the application is secure.
